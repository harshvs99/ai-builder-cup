# Relay: implementation plan

> Relief messaging for when the towers go down. Every villager's phone becomes a mesh node.
> Gemma on the device turns a spoken need into a packet of about 100 bytes. The packet hops
> phone to phone over Bluetooth Low Energy using Relay's own mesh protocol. At the first
> phone with signal, a Gemini agent turns the packets into a prioritised needs map for the
> district control room, and a confirmation travels back through the mesh.

Everything in this document is built inside `Relay - Sustainability & Social Impact/` (referred to below as the Relay folder).

Legend: **[V]** verified (source or method inline). **[A]** assumption, to be measured or confirmed. Unmarked statements are design choices, not claims.

---

## Decisions (Oct 2026)

1. **Transport = Relay's own BLE GATT mesh**, written in Kotlin by us, Apache-2.0. Bitchat's install base in Odisha/Leyte is near zero [A], so we cannot ride bitchat phones, but its protocol is a field-tested design. We **fork the spec, not the network**: the outer frame is byte-compatible with the bitchat v1 packet (public domain, Unlicense), re-implemented from the public-domain iOS sources and our `protocol/SPEC.md`. No code from bitchat-android (GPL-3.0), which avoids a one-way licence door.
2. **Own service UUID.** Bitchat bridge mode (also hosting bitchat's service UUID `F47B5E2D-4A9E-4C5A-9B3F-8E1D2C3A4B5C`) is a later, flag-gated increment. Joining bitchat's network by default means relaying its chat traffic (airtime, battery) for little reach.
3. **Packet types 0x70–0x73** (NEED, ACK, HELLO, INVENTORY). We will ask bitchat maintainers to reserve 0x70–0x7F.
4. **Hand-rolled fixed binary payloads, not protobuf.** Deterministic sizes, no codegen in two languages, and shared golden vectors (`protocol/vectors.json`) enforce Kotlin/Python parity.
5. **ACK text limit raised to 112 bytes** (from 80). Odia and Devanagari are 3 bytes per code point, and 80 bytes cut a short Odia confirmation mid-word [V: test vector]. ACK frame max 175 B, still one BLE write at the 185-byte minimum MTU.
6. **Nearby Connections is kept, for bulk only:** phone-to-phone distribution of the APK and the Gemma model (hundreds of MB over Wi-Fi). Not the message path. After a cyclone the binding constraint is Relay's own install base, not radio range. Play Store's offline "Share apps" was retired [V: Play Store 44.1, Dec 2024, https://www.neowin.net/news/share-apps-functionality-on-google-play-is-going-away-soon/]; Files by Google Quick Share is the manual fallback.
7. **Message path is GMS-free** (BLE + framework `LocationManager` for GPS). Google Play Services is used only for bulk sharing.
8. **Routing never runs in the cloud.** Mesh routing (flood + anti-entropy) is entirely on-device. The cloud does aggregation, Gemini triage, dispatch, ACK and bulletin generation.
9. **POC backend uses SQLite + polling** behind a repository interface. Production path = Firestore + Pub/Sub (next increment, verified against the Firestore emulator).
10. **All cloud infra is Terraform** (`infra/terraform/`), with `infra/deploy.sh <PROJECT_ID>` (Cloud Build image → terraform apply → healthz check) and `infra/destroy.sh <PROJECT_ID>` for clean teardown and rebuild. Reason: hackathon iteration speed and zero leftover cost.
11. **One Cloud Run service `relay`** serves both the API and the built dashboard (same origin, no CORS). This **replaces Firebase Hosting**, which is dropped from the plan. Region default `asia-south1` (Mumbai, nearest Odisha).
12. **Firestore Native uses a named database** (`relay-<suffix>`, `deletion_policy = DELETE`) so destroy/rebuild is clean. Pub/Sub topic `relay-packets` with a push subscription (OIDC) to `/internal/triage` on the same service, plus a dead-letter topic. Gemini via **Vertex AI** with the service's own service account (no API key). The device key is generated by Terraform into Secret Manager.
13. **Backend store is pluggable:** `RELAY_STORE=sqlite` (local POC, default) or `firestore` (cloud). Without `RELAY_PUBSUB_TOPIC`, triage runs in-process.

## 1. Goals and non-goals

### Must have (the demo moment)
1. Four Android phones: three in airplane mode with only Bluetooth switched back on, and one online.
2. On phone A, someone records the voice note *"my mother needs insulin, near the school"*.
3. The phone converts speech to text and Gemma classifies it **offline** into a compact packet: category `MEDICAL`, high urgency, item "insulin", landmark "school", plus GPS.
4. The packet takes at least two hops (A → B → D, with C as an optional third relay) and reaches gateway phone D.
5. D uploads the packet. A Gemini agent clusters, prioritises and drafts a dispatch, and the ticket appears on the **control-room map**.
6. A confirmation, translated into the requester's language, travels back A ← B ← D and shows on phone A.

### Should have
- Store-and-forward: a phone that walks from one cluster to another carries messages across (delay-tolerant networking).
- Duplicate collapse: exact duplicates are dropped in the mesh, and near-duplicates (same need, same place) are merged before dispatch.
- Supported languages: English, Hindi and Odia (Odisha), and Tagalog, Waray and Cebuano (Leyte).
- A human operator approves dispatches on the dashboard.

### Non-goals for v1
- iOS app. The protocol is CoreBluetooth-implementable (bitchat iOS proves the GATT design), so this is a scope cut, not an architectural one.
- End-to-end encryption and strong identity. The frame already carries `HAS_SIGNATURE` + a 64-byte signature slot (ignored in v1, kept when relaying), so signatures can be added later (§4.3).
- Sending voice or images over the mesh. Only text packets travel.
- True routing protocols such as AODV or BATMAN. We use flooding plus anti-entropy, which is enough at village scale.
- Control-room bulletins (§7.5) and SMS uplink (§2a): designed for, not in the v1 spec.

## 2. System architecture

```
 ┌─────────── OFFLINE MESH (airplane mode, Bluetooth on) ───────────┐       ┌───────────── CLOUD (target) ─────────────┐
 │                                                                  │       │                                          │
 │ Phone A (origin)    Phone B (relay)      Phone D (gateway)       │ HTTPS │  Cloud Run: POST /v1/sync (ingest)       │
 │ ┌──────────────┐    ┌────────────┐       ┌──────────────┐        │ ────► │        │                                 │
 │ │ Voice → ASR  │BLE │ store &    │  BLE  │ store &      │        │       │        ▼                                 │
 │ │ rules/Gemma  │GATT│ forward    │  GATT │ forward      │        │       │  Pub/Sub ──► triage worker               │
 │ │ → NEED frame │───►│ dedupe     │ ────► │ + uplink     │        │       │               (Gemini on Vertex AI)      │
 │ └──────────────┘    └────────────┘       └──────────────┘        │ ◄──── │        │ cluster · score · draft ·       │
 │        ▲                  ▲                      │               │ ACKs +│        ▼ translate                       │
 │        └── ACK frame ─────┴──── ACK frame ───────┘               │ bulle-│  Firestore ──► control-room dashboard    │
 │                                                                  │ tins  │                (map)                     │
 └──────────────────────────────────────────────────────────────────┘       └──────────────────────────────────────────┘
   uplink = any validated network: patchy cell · emergency cell site · satellite Wi-Fi · direct-to-cell satellite
```

Every phone runs the **same APK**. A phone becomes a gateway automatically when
`ConnectivityManager` reports a network with `NET_CAPABILITY_VALIDATED`.

**Why the agent runs in the cloud and not on the gateway phone:** the control-room map
needs a shared backend anyway. Running the agent server-side also keeps API keys off
villagers' phones, and lets several gateways feed one picture. The gateway phone stays a
thin uplink: it uploads frames and downloads ACKs.

## 2a. Getting data out: the uplink ladder

Any Relay phone with validated internet auto-becomes a gateway. Gateways are opportunistic and mobile (data mules), not fixed infrastructure. Ladder, most to least likely:

1. **A villager walks into patchy surviving coverage** and syncs everything carried (DTN). Needs no one else's equipment.
2. **Telco emergency cell sites** after cyclones. [A: standard practice for Indian and Philippine carriers; not verified for 2026.]
3. **Responder satellite Wi-Fi at relief camps / block offices.** One phone on it is the gateway for the whole mesh; a sync batch is a few KB.
4. **Direct-to-cell satellite data.** Android "constrained satellite networks": the app opts in via manifest meta-data `android.telephony.PROPERTY_SATELLITE_DATA_OPTIMIZED` and a `NetworkRequest` that removes `NET_CAPABILITY_NOT_BANDWIDTH_CONSTRAINED` [V: https://developer.android.com/develop/connectivity/satellite/constrained-networks]. Carrier availability in India/Philippines is unverified; we opt in because it is free.
5. **SMS uplink (plan option, not POC).** A NEED payload is 81–118 B (max 118, SPEC §5.1; frame ≤ 140 B) and fits one 140-byte binary SMS. SMS often recovers before data [A]. Play policy restricts `SEND_SMS` [A], so it would use a user-confirmed compose intent or a sideloaded build.

Design consequence: the sync batch stays tiny and idempotent, so any rung that works for a few seconds is enough.

## 4. Wire protocol

**`protocol/SPEC.md` is the source of truth.** If code and SPEC disagree, the code is a bug. This section is a summary only; do not duplicate the spec here.

### 4.1 Summary
- **Outer frame:** bitchat v1 compatible (14-byte header, +8 sender, optional recipient/signature), big-endian, version 1 only, TTL 7 for `NEED`/`ACK`.
- **Types:** `0x70 NEED` (broadcast), `0x71 ACK` (directed to `target_node`), `0x72 HELLO`, `0x73 INVENTORY` (the last two never relayed). `0x74 BULLETIN` is future, not in v1.
- **Payloads:** fixed binary layouts, 1-byte `payload_version`, length-prefixed UTF-8 strings truncated on code point boundaries.

### 4.2 Size budgets (enforced by tests)
| Item | Payload | Frame |
|---|---|---|
| `NEED` | ≤ 118 B | ≤ 140 B |
| `ACK` | ≤ 145 B | ≤ 175 B |
| `INVENTORY` chunk | ≤ 156 B (19 ids) | ≤ 178 B |
| Minimum ATT MTU | 185 (182 usable) | every frame fits in one write |

### 4.3 Forward compatibility
- Unknown types and unknown payload versions are deduplicated by an opaque key and relayed if `ttl > 1`, never stored or shown.
- Signatures (`HAS_SIGNATURE`, 64 B) are carried but ignored in v1; Ed25519 anti-spoofing is a v2 task.

## 5. Android app

**Stack:** Kotlin, Jetpack Compose, Coroutines/Flow, framework Bluetooth LE APIs and
`LocationManager` (message path is GMS-free), Room for store persistence, LiteRT-LM for
Gemma (post-POC), and `play-services-nearby` only for the bulk-share feature. Recommended
minimum is Android 10; Android 12+ is targeted.

### 5.1 Mesh transport (`app/`, BLE)
- **Dual-role GATT:** every node is a peripheral (GATT server, advertising the Relay service UUID) and a central (scanning with a `ScanFilter` on that UUID, connecting as GATT client). UUIDs and properties are in SPEC §2.
- **One characteristic**, write/notify: centrals write frames, peripherals notify them. **One whole frame per write**; no link-layer fragmentation in v1.
- **MTU:** 517 requested, 185 minimum; a link that negotiates less is closed.
- **Link cap:** 4 central, 7 total. **Duplicate-link rule** from SPEC §2: after both `HELLO`s, keep the link where the lower `node_id` is central, close the other.
- **Foreground service** of type `connectedDevice` with a persistent notification, so the mesh survives screen-off and Doze.
- **Android BLE realities to engineer around** (numeric limits are **[A]**, measured in the field test, §11):
  - GATT error 133: close the `BluetoothGatt`, back off, retry.
  - Serialize GATT operations per connection (one outstanding op).
  - Scan throttling: about 5 scan starts per 30 s, so one long-lived scan with duty cycling, not restarts.
  - Screen-off scans only deliver results with filters set.
  - OEM variance in stacks, background limits and connection caps; test on every phone in the demo set.
- **Swap point:** transport sits behind the `GossipNode` `LinkSender` interface, so a different bearer (including Nearby Connections) can replace BLE without touching gossip. Two-way door.
- **Permissions:** `BLUETOOTH_SCAN/ADVERTISE/CONNECT`, `ACCESS_FINE_LOCATION` (GPS, and BLE scan on older versions), `RECORD_AUDIO`, `FOREGROUND_SERVICE_CONNECTED_DEVICE`, `POST_NOTIFICATIONS`. `NEARBY_WIFI_DEVICES` (`neverForLocation`) and `ACCESS/CHANGE_WIFI_STATE` are requested **only** by the bulk-share feature (§7a), never on the message path. A first-run wizard walks the user through them.

### 5.2 Gossip engine (`core-protocol/`, behaviour per SPEC §6)
An epidemic store-and-forward protocol:
1. **Link up:** send `HELLO`, then chunked `INVENTORY` (≤ 19 ids per chunk). On the peer's inventory, push every stored NEED/ACK it lacks to that link only, **timestamp restamped to now**, TTL unchanged. This is anti-entropy; it delivers messages that arrived while two phones were apart.
2. **New frame** (local or received): check the seen-set (LRU, 10,000 keys). If new, store it, deliver to the app, and if `ttl > 1` forward to every link except the sender with `ttl − 1` after a **jitter of 10–220 ms**. Initial TTL 7.
3. **ACK routing:** ACKs flood the same way. Only the node whose ID equals `target_node` shows the ACK; everyone else relays it.
4. **Expiry:** NEED/ACK frames older than 72 h are deleted from the store; their keys stay in the seen-set until LRU eviction. Dedupe on `msg_id` / `ack_id`.
5. **Uplink bias (stretch):** `hops_to_gateway` from `HELLO` builds a simple gradient. When link slots are scarce, prefer peers with a lower value.

All of this lives in `core-protocol`, which has no Android dependencies, so `simulator/` and the unit tests run the exact same code.

### 5.3 Turning speech into a packet (rule extractor in `core-protocol/`; ASR + Gemma in `app/`, post-POC)
```
voice note ─► ASR (offline) ─► transcript ─► Gemma (JSON-constrained) ─► validate ─► NEED
                                         └─► rule-based extractor (fallback / cross-check)
```
- **ASR:** use Android `SpeechRecognizer` with `EXTRA_PREFER_OFFLINE` and pre-downloaded
  language packs. If the chosen Gemma E2B build accepts audio input, the phone sends audio
  straight to the model and skips the separate ASR step. Decided in Phase 8 after testing on our phones.
- **Model tiering,** chosen at runtime:
  | Device | Model | Why |
  |---|---|---|
  | ≥ 6 GB RAM | Gemma 4 E2B (int4) | Better multilingual understanding, can handle audio |
  | Lower-end | Gemma 3 270M, **fine-tuned** (int8) | About 300 MB, fast on any phone |
  | Model fails, times out (> 4 s) or gives invalid JSON | Keyword/regex extractor | The demo never dead-ends |
- **Prompt contract:** the model returns only the JSON shape of `NEED`, with enum values
  listed explicitly. The parser rejects or repairs bad output; for example, it clamps
  enums and truncates strings to their byte limits.
- **The user stays in control:** before sending, phone A shows the parsed card
  (🩺 Medical · Insulin · near School · 1 person, elderly). The user can tap to fix a
  field. This also makes the demo easy to read on video.
- **Model distribution:** there will be no internet after the cyclone, so the model ships
  with the app (Play Asset Delivery install-time pack, or sideloaded for the demo), and spreads
  phone to phone through Nearby bulk share (Phase 9, §7a).

### 5.4 Duplicate collapse
- **Exact:** the `msg_id` seen-set means a frame is never stored or forwarded twice.
- **Origin-side:** if the same user re-records a need with the same category and item
  within 30 minutes, the phone updates the existing packet instead of creating a new one.
- **Near-duplicate (backend):** two `NEED`s with the same category, the same
  geohash-7 cell (about 150 m) and a matching item within 6 h are linked. Relays still
  forward both; this keeps mesh correctness simple. The backend merges them into **one
  ticket with a report count**, so the control room sees one corroborated need instead of
  five rows.
- **Stretch:** relays suppress near-duplicates and send a 16-byte `CORROBORATE{ref, +1}`
  instead.

### 5.5 Gateway (`app/`)
- `NetworkCallback` watches for a validated network. The app then flips `IS_GATEWAY` in `HELLO`
  and starts a sync loop: every 10 s while online, plus immediately when a new frame arrives.
  It also registers the constrained-satellite opt-in (§2a, rung 4).
- `POST /v1/sync {gateway_node, frames[] (base64 outer frames), ack_cursor}` returns
  `{accepted, duplicates, rejected, acks[] (base64 ACK payloads), ack_cursor}`. Uploads are
  idempotent on `msg_id`; the backend derives `hops = 7 − ttl`. Full contract: SPEC §7.
- The gateway wraps each returned ACK in a frame (`sender_id` = gateway, `recipient_id` =
  `target_node`, TTL 7) and originates it into the mesh.
- Several gateways may upload the same frames; the backend dedupes on `msg_id`.

### 5.6 Screens
1. **Home:** a big *Hold to speak* button, the mesh status (peers nearby, gateway reachable
   N hops away), and the user's sent needs with live status (Queued → Relayed → Received
   by control room ✓).
2. **Confirm need card:** the parsed fields, editable, with a Send button.
3. **Relay view (debug/demo):** peers, frames carried, and the hop trail per frame. This
   is useful in the video.
4. **Settings/debug:** a node ID allowlist that forces a **chain topology** (§9), a model
   switch (E2B / 270M / rules), a "pretend offline" toggle, and a button to clear the store.

## 5a. Experiments (not on the critical path)

Rule: baseline first. Nothing below ships unless it beats the GATT mesh on delivery rate or range in our own corridor test (§11).

- **(a) LE Coded PHY + extended advertising** as a connectionless long-range bearer. Bluetooth 5 Coded PHY gives about 4x range on paper; budget-phone results are poor in public reports (one Nordic DevZone report: ~20 m on a Nokia 2.3, https://devzone.nordicsemi.com/f/nordic-q-a/79044/nrf-connect-android-poor-distance-even-with-coded-phy-s8-long-range/327271). One anecdote, so treat as a warning, not a measurement.
- **(b) Wi-Fi Aware bearer** on phones that support it. Higher throughput, same `LinkSender` swap point.
- **(c) Bitchat bridge mode** (also host bitchat's service UUID; frames need no translation). Verified finding: stock bitchat iPhones store and re-sync `groupMessage` (0x25) broadcasts for 6 h without signature checks [V: bitchat iOS commit 5e9287f, `GossipSyncManager.swift` ~L306, `BLEService.swift` `handleGroupMessage`], which would give store-and-forward through stock iPhones. We do not build on it: it rides a type with other semantics, and Android bitchat does not store it.

## 6. Gemma fine-tuning (`ml/`, Phase 8)

Gemma 3 270M is meant to be fine-tuned for narrow tasks. Without fine-tuning it will not
reliably produce our JSON, especially for Odia or Waray input.

1. **Dataset:** Gemini generates about 5,000 synthetic distress utterances across six
   languages, including code-mixed speech (Hinglish, Taglish) and ASR-style noise (no
   punctuation, misheard words). Each utterance comes with its gold JSON. A human
   spot-checks 200 of them. 500 are held out for evaluation.
2. **Fine-tune:** LoRA via Hugging Face TRL/PEFT (or KerasNLP) on Colab or a single
   L4/A100. Then merge the adapters.
3. **Convert:** export to LiteRT (`.litertlm` / `.task`) with int8 weights, and check the
   result in the Google AI Edge Gallery app before integrating it.
4. **Evaluate (`ml/eval/`):** category accuracy, item and landmark exact match, JSON
   validity rate, and p50/p95 latency on a mid-range phone.
   **Targets:** ≥ 90 % category accuracy, ≥ 98 % valid JSON after repair, and p95 < 3 s
   for 270M.
5. **E2B:** use it with a few-shot prompt first and fine-tune only if the evaluation says
   it is needed.

## 7. Backend and Gemini agent (`backend/`)

Recommendation: run the POC on SQLite behind a repository interface (`RELAY_STORE=sqlite`, default), and deploy the same service to managed GCP with one command. The mesh does not change between the two.

### 7.1 Production target (Phase 7, Terraform)
One Cloud Run service `relay` (region default `asia-south1`) serves the API **and** the built dashboard: same origin, no CORS, no separate hosting product.
| Layer | Service | Role |
|---|---|---|
| Ingest + UI | **Cloud Run** `relay` (FastAPI, stateless, scale-to-zero) | `/v1/sync`: validate, dedupe on `msg_id`, publish, return ACKs. Also serves the dashboard. Ingest target < 100 ms **[A]** |
| Buffer | **Pub/Sub** `relay-packets`, push subscription (OIDC) to `/internal/triage` on the same service, dead-letter topic | Absorbs bursty gateway uploads (many gateways reconnect at once when coverage returns); failed triage lands in the DLQ, not lost |
| Triage | **Gemini on Vertex AI**, function calling (or ADK), via the service's own service account (no API key) | Triage reasons, ±1-tier priority adjustment, dispatch drafting, translation. The score itself stays deterministic |
| Record | **Firestore Native**, named database `relay-<suffix>`, `deletion_policy = DELETE` | System of record. The dashboard reads through the same-origin API (polling); Firestore listeners are an optional later upgrade |
| Secrets, ops | **Secret Manager** (device key generated by Terraform), Cloud Logging/Monitoring | No keys in images or on phones beyond the device key |

**Infra as code:** everything above is `infra/terraform/`. `infra/deploy.sh <PROJECT_ID>` = Cloud Build image → `terraform apply` → healthz check. `infra/destroy.sh <PROJECT_ID>` removes it all. The named database and DELETE policy are what make destroy/rebuild clean; the aim is zero leftover cost.
**Multi-gateway fusion:** several gateways uploading the same frames dedupe on `msg_id`; the ticket records every gateway that saw it.
Consequence: idle cost near zero (scale-to-zero) **[A]**; load is KBs per sync; five managed services, no clusters.

### 7.2 What the POC does today
FastAPI + SQLite behind a repository interface; a **deterministic agent** (clustering, scoring, templated dispatch and ACK text) with **optional Gemini** (locally via `GEMINI_API_KEY`; `GEMINI_MODEL`, default `gemini-flash-latest`; in the cloud via Vertex AI and the service account). The dashboard polls every 2 s. `RELAY_STORE=firestore` swaps the store; without `RELAY_PUBSUB_TOPIC`, triage runs in-process. Firestore parity is checked against the emulator before any real project is touched.
**State of the POC:** everything is verified locally. The cloud deploy is one command (`infra/deploy.sh`) pending a GCP project and credentials; it has not been run against a real project.

### 7.3 Data model (SQLite tables now, Firestore collections later)
- `packets/{msg_id}`: the raw decoded packet, the gateway(s) that received it, hops, and when.
- `tickets/{ticket_no}`: the canonical need, `report_count`, the linked `msg_id`s,
  `priority_score`, `priority_reason`, `status`, `dispatch_draft{en, local}`, and
  `assigned_to`.
- `acks/{id}`: queued confirmations, with `target_node`, `ref_msg_id`, text and a delivered flag.

### 7.4 Agent loop (triggered by each `/v1/sync` batch)
Gemini runs with function calling when enabled; the deterministic agent implements the same tools without it.
| Tool | What it does |
|---|---|
| `get_new_packets()` | Returns the packets that are not yet linked to a ticket |
| `find_similar_tickets(packet)` | Searches by geohash and category, with Gemini judging "same need?" |
| `upsert_ticket(...)` | Creates a ticket or merges a packet into one, and increments the report count |
| `score_priority(ticket)` | **Deterministic** score (below). Gemini only writes the human-readable reason |
| `draft_dispatch(ticket)` | A short dispatch in the district emergency operations centre's format: what, who, where (coordinates + landmark + nearest village), urgency, report count |
| `translate(text, lang)` | Gemini translation of dispatch drafts into Odia, Hindi, Tagalog, Waray or Cebuano |
| `queue_ack(ticket, status)` | Writes the ACK, which the next gateway sync picks up |

**Priority score** (in code, so it is explainable and stable):
`score = category_weight (RESCUE/MEDICAL highest) + urgency×w + vulnerability flags + log(people) + log(report_count) + hours_waiting×w`.
Gemini may adjust the score by at most ±1 tier, and it must give a reason. The dashboard shows that reason.

### 7.5 Downlink: ACKs and bulletins
- **ACKs:** an automatic `RECEIVED` ACK when a ticket is created (*"Your request #142 for insulin has reached the control room"*), and `DISPATCHED` when an operator approves. **ACK text always comes from byte-checked templates** (≤ 112 B per language), never free-form LLM output: a mistranslated or truncated confirmation is a safety failure.
- **Bulletins (new idea):** control-room messages for everyone (e.g. "relief camp open at X school, water at 4 pm") go down through every gateway and flood to all phones. Needs a `BULLETIN` type `0x74` and a v1.1 spec change. **Future; not in v1.** Text would come from operator input plus translation, reviewed before send.

### 7.6 API (SPEC §7 is authoritative)
- `POST /v1/sync`: gateway upload and ACK download, protected by a device key (`X-Relay-Key`), enough for the hackathon.
- `GET /v1/tickets`, `GET /v1/tickets/{ticket_no}`, `GET /v1/stats`: dashboard reads.
- `POST /v1/tickets/{ticket_no}/approve`: marks the ticket dispatched and queues a `DISPATCHED` ACK per linked origin.
- `POST /v1/dev/inject`: development only; injects fake needs so the dashboard can be built without phones.

## 8. Control-room dashboard (`dashboard/`)

**Stack:** Vite + React + TypeScript, MapLibre GL with OSM tiles. POC: polls the backend
every 2 s, in the cloud as well (same-origin API on the `relay` Cloud Run service, which also serves
the built dashboard). Firestore live listeners are an optional upgrade, not planned for v1.

- **Map:** pins coloured by category and sized by priority. Clusters merge as you zoom
  out. A new ticket animates in, and this is the hero shot for the demo.
- **Ticket queue:** sorted by priority. Each row shows the category icon, a one-line
  summary, the report count, time waiting and hop count.
- **Ticket detail:** the original summary, how the request was understood, the priority
  reason, the hop count and gateways, and the dispatch draft in English and the local
  language. An **Approve & dispatch** button sends the confirmation.
- **Header stats:** open needs by category, and gateways online.

## 9. Demo setup and the two-hop risk

The risk the brief names is mesh reliability beyond two hops. We address it in two ways.

**Engineering:**
- In one room, every phone sees every other phone, so the packet would go A → D in a
  single hop. The **debug allowlist** forces a chain (A↔B, B↔C, C↔D): a link to a node ID
  outside the allowlist is dropped after `HELLO`, so the hops in the video are real.
- The simulator tests flooding, ACK return and dedupe on 4-, 10- and 50-node topologies,
  including random link drops, before we rely on real phones.
- Expect about 10–30 s for discovery and connection per hop **[A, measure in Phase 6]**. Keep
  scanning and advertising running, and pre-connect the chain before recording starts.

**Runbook (`docs/demo-runbook.md`):**
1. Four phones, all charged, with the APK and models installed and the language packs
   downloaded.
2. Phones A, B and C: turn on airplane mode, **then turn Bluetooth back on**.
   Location stays on.
3. Phone D: mobile data on. Confirm the gateway badge is showing.
4. Turn on the chain allowlist, use the video length of **two hops (A → B → D)** that the
   brief recommends, and keep C as a hot spare relay.
5. Open the dashboard on a laptop, start recording, then speak into A.
6. Have a pre-recorded backup take, plus a `/v1/dev/inject` fallback in case venue radio
   noise breaks the live run.

## 11. Testing strategy
- **`core-protocol` unit tests:** codec round-trip, golden vectors, the size limits, dedupe,
  TTL expiry, ACK targeting, and inventory chunking and diffing.
- **Simulator scenarios:** chain, star, partitioned clusters bridged by a "walking" node,
  and 20 % link loss. Measure delivery ratio, latency in rounds, and duplicate
  transmissions. A real-HTTP e2e scenario drives the actual backend.
- **Codec parity:** the Python and Kotlin codecs both run `vectors.json` in CI.
- **NLU evaluation:** `ml/eval` runs on the held-out set and on a small set of real
  recorded utterances from team members in each language.
- **Backend:** pytest for priority scoring and merging, plus recorded Gemini responses so
  the agent tests are deterministic in CI.
- **Field tests:** a corridor or outdoor test to find the real BLE range and delivery rate
  between hops, GATT error-133 rate, achieved MTU and scan behaviour per OEM (this is where
  the [A] numbers in §5.1 get replaced with measurements), and a 2-hour battery drain test
  with the mesh service running.

## 12. Risks and mitigations
| Risk | Mitigation |
|---|---|
| **Android BLE GATT reliability across OEMs (top risk)** | The transport sits behind `GossipNode`'s `LinkSender`, so Nearby Connections can be swapped in as a message bearer (two-way door). Error-133 retry, serialized GATT ops, anti-entropy on every reconnect, a chain allowlist for the demo, and a simulator for confidence at scale |
| **Install base after a disaster** (the mesh needs Relay on enough phones) | Pre-position the APK through OSDMA / NGOs / volunteers before the season; Nearby bulk share spreads APK + model phone to phone afterwards; Quick Share via Files by Google as manual fallback |
| The mesh is flaky beyond two hops | Anti-entropy, a two-hop video, and a simulator for larger topologies |
| Gemma 270M quality in Indic or Philippine languages | Fine-tune on synthetic multilingual data, use E2B on capable phones, keep the rule fallback, and let the user correct the card |
| Offline ASR is missing for Odia or Waray | Try E2B audio input; otherwise fall back to Hindi/Filipino/English ASR, or let the user type or pick an icon (🩺 💧 🆘 🍚 🏠) as a no-ASR path |
| Model size and RAM | Runtime tiering, int4/int8 quantisation, and lazy loading of the model only while recording |
| Battery drain from continuous advertising and scanning | Duty-cycle scanning when idle (for example 30 s on / 60 s off) and keep advertising on. Full duty cycle only while there are unsent frames |
| Spoofed or abusive messages | v1: rate-limit per origin node and require operator approval. v2: signatures (§4.3) |
| Venue RF congestion during judging (2.4 GHz) | Pre-recorded backup video and the dev inject endpoint |
| Android background limits kill the service | Foreground service, a battery optimisation exemption prompt, and testing on each OEM in the demo set |
